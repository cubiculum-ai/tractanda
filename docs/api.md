# API and agent integration

Use executable help and `TractandaStore/describe` as the operational reference for this experimental API. The local capability is `https://tractanda.ai/ns/local-prototype/4`, not a published network JMAP extension.

`Item` is the concrete generic class and the superclass of the specialized families. `classID == "Item"` selects generic items; `kMDItemContentTypeTree == "Item"` includes all classes. Older prototype clients using capability `/2` must be updated and reconnected before using this server.

## Native API and daemon

The native CLI sends ordered JSON method calls over a Unix socket:

```sh
tractanda call /tmp/tractanda-demo.sock TractandaItem/query \
  '{"expression":"subject ==[cd] \"*design*\"","limit":16}'
tractanda get /tmp/tractanda-demo.sock ITEM_ID
tractanda describe /tmp/tractanda-demo.sock
tractanda describe /tmp/tractanda-demo.sock properties
tractanda extracted-text /tmp/tractanda-demo.sock ITEM_ID
```

Native `connectionFailed` diagnostics retain an optional numeric `osError` and the underlying OS error text. `EPERM`/`EACCES` report socket permissions or command-sandbox restrictions and return without attempting managed startup; they do not establish that a server has stopped. This diagnostic change is pending in source, alongside the attachment feature.

The envelope is `{ "using": [CAPABILITY], "methodCalls": [[METHOD, ARGUMENTS, CALL_ID]] }`; the CLI unwraps one result. Socket peer credentials establish the caller—arguments cannot select another actor. The CLI, TUI and `tractanda-mcp SOCKET` stdio adapter continue to use this Unix route.

The daemon adds optional loopback HTTP in the same process:

```sh
tractanda daemon STORE SOCKET --index-directory INDEX_DIRECTORY --http-port 48728
```

`STORE` and `SOCKET` are separate positional arguments. Omit `--index-directory` to retain the compatible `STORE/index` layout; its selected external directory may contain only derived SQLite/FTS, Vec1 and learning-cache files. `--no-http` is native-only. The optional presentation parameters are exactly `--view ID` or `--project-root ID --status-root ID [--project ID]`.

## HTTP authentication and MCP

HTTP `/auth/login` accepts an OS username and password, then `/api` and `/mcp` require its bearer token. On macOS the password path uses OpenDirectory. Linux arbitrary-user verification needs the separate privileged PAM helper deployment; its host installation and real credential tests are pending. Do not run the daemon as root merely for PAM.

`TractandaAuth/createSession` is special only on the native socket: an envelope with that one method and empty arguments issues the peer's **own** session token. It rejects UID selection. The same method over HTTP does not mint a token.

`/mcp` implements Streamable HTTP JSON. A session is bound to the authenticated principal; sessions and in-flight requests are bounded globally and per user, expire when idle, and are re-authorized on each request. There is no SSE endpoint or event replay. Clients initialize with HTTP POST, retain `Mcp-Session-Id`, and may DELETE that session. stdio MCP remains a separate local adapter.

For stdio, omit `--profile` to use the configured default. `--profile default` selects a literal profile with that name; it is not a special default alias. User defaults precede the system default, and several local aliases may resolve to one socket. The adapter captures that selection at startup; restart it after changing connection settings.

`tractanda_info` adds `connection` diagnostics: `transport`, the selected `profile`/`profileSource` and `socketPath` where applicable, expected server account, adapter identity and `referenceRevision`. Native-call failures retain this local block with `status: "error"` and the original error, without cached server facts. A successful response has `status: "ready"`; when native feature `tractanda.runtime-identity.v1` is declared, `server` contains release version, executable SHA-256 when readable, process ID and process instance ID. A source build without a matching bundle manifest reports version `development`; its digest distinguishes builds but does not prove feature support. The integrated HTTP adapter reports `transport: "inProcess"`, with no fabricated socket/profile, and cannot answer while its server process is down.

Native `TractandaStore/info` returns a `features` array of versioned behavior IDs. This build declares `tractanda.runtime-identity.v1`, `tractanda.semantic-job-timing.v1`, `tractanda.live-seek-cursor.v1`, and `tractanda.attachment-lifecycle.v1` (among other features). These identify API support, not authorization or model availability. The MCP adapter compares fresh declarations with its `requiredServerFeatures` in `connection.referenceCompatibility`: `satisfied` when all listed requirements are declared, `missingFeatures` plus `missingServerFeatures` when a valid declaration omits them, `unverified` when the declaration is absent/invalid, and `unavailable` when native info failed, and `protocolMismatch` when the reachable native server explicitly rejects the adapter capability with `unsupportedCapability`. This distinction does not establish which side is older. Extra unknown feature IDs are ignored. Skew does not make otherwise successful info a tool error. Neither build hashes nor cached declarations substitute for current feature support. An advertised feature with missing required fields is a contract violation; undeclared support is unverified.

MCP reference resources are compiled into the adapter, while `tractanda_describe` is served by the native backend. References remain static during an adapter process; this preview advertises neither resource subscriptions nor list-change notifications. Restart/reinitialize after an upgrade and refresh discovery. The initialize version includes build and reference digests; `connection.referenceRevision` is the full reference-text cache key. If only the native server restarted, its process instance changes independently of the stdio adapter.

## Permissions and administration

All reads, writes and history requests use current item permissions; changing access affects historical visibility too. OS identity and group membership are refreshed per request. An optional `AccessConfigurationItem` has profile `tractanda.access.v1`; `administration: "system"` recognizes root plus `admin` on macOS or `sudo` on Linux, unless `administratorGroup` overrides the OS group. Without an access configuration, legacy `serviceOwner` administration remains in effect pending migration.

## Guarded changes and compact retrieval

Saved views are a capability of ordinary items carrying `viewDefinition`; no dedicated view class is needed. `viewDefinition.presentation.sections` is an ordered list of category references. Saved-view clients preserve that order. Implicit project boards use it as a preferred sequence and append other eligible status leaves; otherwise, they traverse the Status hierarchy with siblings ordered by integer `categoryOrder` (default zero), then name and ID. Status names are data, not built-in client behavior.

A category with the valid selection expression `itemID == ""` has no direct rule matches, allowing shared/manual or personal assignments to determine membership; child categories can still contribute inherited members. Shared `categoryOverrides` live on the target item. A caller-owned `PersonalStateItem` has an unpinned `target` reference and `personalOverrides`, taking precedence for that caller. Removing a personal override falls back to shared decisions/rules. These operations change categorization, never access rights.

Ordinary actions use `Item` and category assignments for to-do, waiting and other workflow states. Change membership to change those states; no class transition is needed. Every item may carry `waitingOn` as a tagged reference to a person/event or explanatory text, or leave it unset. Category rules and manual overrides determine membership independently of that property. Discover supported concrete types with `TractandaStore/describe` (`topic: "types"`).

Kanban preserves native query order. The optional sample Project definition sorts by Priority **category membership**. Project-specific `viewDefinition.sort` and `presentation` override those defaults independently, without inheriting selection criteria. With neither definition supplying a sort, normal modified-time order applies. Priority, urgency, work type, assignment and optionality are categories; the client does not write parallel scalar fields. `sortOrder` remains optional ordinary metadata only for explicit saved sorts and is never populated by browser saves.

In the TUI view editor, enter `category:<axis UUID>` as a sort or column target; ordinary field names continue to address owned metadata.

Paged queries containing a category comparator stream current authorized candidates and retain only identity plus selected scalar comparator keys for the sorted `position + limit` prefix. They count all exact matches without the bulk 512-match ceiling, but enforce a 16 MiB aggregate serialized-key window budget. Large or deep windows can return `resourceLimit`; no partial page/count is reported. Each position page recomputes membership and ordering, including saved-view pages, with the requested evaluation clock and current permissions. This is a bounded fallback scan, not indexed category-sort acceleration. Nonpaged bulk category queries retain their 512-match/16 MiB contract; property-only custom-sort fallback behavior is unchanged.


A query sort has up to four distinct targets: `{"property":"modifiedAt","isAscending":false}` or `{"categoryRootID":"<axis UUID>","isAscending":true}`. Category comparators use effective membership in ordered immediate children (`categoryOrder`, name, ID). Descendants inherit into that branch; multiple matches take the first branch. A root exclusion wins, and unranked items stay last in either direction. In canonical `viewDefinition.sort` and `presentation.columns`, `categoryRootID` is a tagged current reference. A column chooses either `property` or `categoryRootID`, with its usual title/width.

`TractandaCategory/memberships` (MCP `tractanda_memberships`) accepts 1–64 `ids`, 1–8 `categoryRootIDs` and optional `at`. It returns `state`, ordered `roots`/children, `memberships[itemID][rootID]` as matching category IDs, and non-disclosing `notFound`. This is an ephemeral ACL-filtered projection, never an item property. A childless root returns its own ID when included. Use a fixed clock and compare state across batches.

Web edits preserve untouched absent fields and unknown metadata. Clearing a nonempty body or working-notes field in the web editor removes its key with `unset`. Untouched absent or explicitly empty values remain unchanged; API clients can still deliberately store empty text. The client writes subject/body/workingNotes, checklist content and changed category overrides only. It does not materialize empty fields or inject dependencies/order values on an unrelated edit.

Tagged values include text, integer, real, boolean, date, bytes, reference, list and object. Use a persisted `operationID` and exact payload; an uncertain mutation is retried with both unchanged. IDs are nonempty text of at most 200 UTF-8 bytes with no NUL characters, scoped to store and authenticated actor. A definite pre-commit rejection does not consume an unused ID, so corrected arguments may reuse it. Reconcile any earlier uncertain attempt first. An exact replay returns `replayed: true` and the original committed revision, not a newer head; current read permission still applies. `unset` is required even when it is `[]`. Existing updates also require the current `expectedRevisionID`. Changes replace whole top-level fields, so fetch and merge a map before replacing it.

Use `date` for timestamps, even though both date and text values are serialized as strings. For `activityNotes` and `activity`, each list element is a tagged object with `at` as a tagged date and `text` as tagged text. For example, `at` can be `{"type":"date","value":"2026-09-08T14:15:34.048628+00:00"}`. The property catalogue returned by `TractandaStore/describe` documents the nested element types as conventions; arbitrary additional fields remain supported.

Imported source times belong in ordinary `originalCreatedAt` and `originalModifiedAt` date fields when known. The service-managed `createdAt` and `modifiedAt` describe the Tractanda item itself. Leave unknown times unset. Dates require an ISO 8601 timestamp with a timezone: do not invent a time or zone for an imprecise source date. Date-tagged values support date comparisons and are omitted from full-text extraction. The current query grammar addresses top-level fields and scalar lists, not nested activity object arrays.

Get/history support `full`, `content`, `summary`, or explicit top-level `properties`. Get is byte-bounded: follow ordered `remainingIDs`, handle `oversizedIDs` with a narrower projection, and compare state. An omitted projected property is not an unset field.

`state`/`queryState` cover the administrator's store, or an ordinary caller's readable revision set and group context. Pages are **live**, never a frozen cross-request result. Keep `at` and `timeZone` fixed across relative-date pages; if intervening edits change the relevant state, restart or reject the traversal and read current results. Every page and count applies current permissions, including after access is revoked. Per-item revision guards decide whether an edit conflicts; an unrelated state change does not require repeating committed imports or abandoning a batch of known item IDs.

With `tractanda.live-seek-cursor.v1`, native `TractandaItem/query` adds an optional opaque `cursor` argument and `nextCursor`/`previousCursor` response fields. Cursor paging currently covers descending `modifiedAt` (the default) or `createdAt`, with no filter or a bounded indexed typed scalar/list predicate that the server evaluates exactly. Administrator and ordinary reads may use these raw all-items, exact classID, and indexed scalar/list shapes. Category selections, saved views, personal overlays, category membership rules, custom sorts, and random access remain on position paging. Other query shapes and random access keep using exact `position` paging. Never send `position` with `cursor`; supplying both is an error. Repeat the query and sort. `at` and `timeZone` may be omitted on continuations to inherit the exact evaluation clock, or repeated unchanged. Page size may change after `responseTooLarge`; page size is excluded from cursor identity.

Cursors are encrypted/authenticated and bound to the canonical store identity/location, current authenticated UID, canonical query, visible `queryState`, order boundary and direction, typed timestamp plus ItemID tie, evaluation clock, and a server-held exact total reference. The input token is capped at 8 KiB. Cursors are continuity markers, not permission grants or client totals. Current identity, ACL, predicates and revisions are checked on each delivery. Relevant visible edits, ACL/group remaps, clock/query/order mismatches, a different caller or store, tampering, process restart, or total-reference cache eviction invalidate the token. Hidden edits that do not change the caller's visible state leave it usable. On `invalidCursor` or `unsupportedCursor`, a client may retry once at the same absolute position with the same clock, but must still compare state before showing results; a changed state restarts from the first page. The TUI does this for eligible pages, including when smaller paired query/get chunks assemble one visible page.

`tractanda_get` and `TractandaItem/get` take an `ids` array, even for one item. Single-item explain/history/revision/resolve calls take `itemID`; `itemIDs` is not an alias.

## Extracted-text diagnostics

`TractandaItem/extractedTextUnit` (MCP `tractanda_extracted_text_unit`) requires freshly declared `tractanda.extracted-text-units.v1`. The shared asynchronous Coordinator declares this installed route; a direct synchronous ItemService backend omits the feature and rejects direct calls with `extractedTextUnitsRequireCoordinator`. Batched unit calls return `singleCallRequired`. Converter/model readiness is independent. It reads one current corpus unit, including saved v2 pages, with mandatory `itemID`, `expectedRevisionID` and zero-based `unit`. Obtain the revision from get/diagnostics. `offset` counts UTF8 bytes (default0); `limit` is1..262144 (default65536); `maxBytes` is8192..524288 (default524288). Follow `next.unit`/`next.offset` with the same revision until null. Misaligned, too-small and zero-progress windows fail. Current ACL/head validation precedes delivery; revision changes require a fresh current read.

The result carries opaque `sourceIdentity.contentHash`, corpus counts, one unit's UTF8 length/window/origin, all at-most512 spans and relevant saved processing coverage. `canonicalVerification` independently compares only the selected canonical window, length, locator and spans; `indexConsistency` describes captured component metadata. `globalPlacementVerified` and `wholeDocumentVerified` are false. Processing coverage does not imply full OCR text or recognition quality. Missing/unready components and mismatches fail explicitly. Native encoded-result and serialized MCP wrapper budgets both apply; reduce `limit` on `responseTooLarge`. Public readers are bounded, cancelled and joined before index replacement; failed lease retirement remains durable.

Existing extracted-text projections describe `sourceScope: inlineFieldsAndRepresentations`; their source text/hash/byte counts do not include saved v2 document pages. `sourceComplete:false`, `omittedDocumentRepresentationIDs` and compact `documentCoverage` identify that gap, while `indexedCorpus` identifies the actual current corpus binding or explicit unready status. Use the unit method for bounded complete-source traversal. Ordinary/inline projections retain their existing limits and errors.

`TractandaItem/extractedText` (MCP `tractanda_extracted_text`) is a read-only diagnostic for **current** revisions. It requires the declared feature `tractanda.extracted-text.v1`. Supply 1–64 distinct canonical UUIDs in `ids`; there is no historical-revision argument.

Choose `projection: "source"` (default) for assembled inline source, `"fts"` for the subject/body/metadata projection of inline extraction, or `"summary"` for identities, byte counts and index status without item text. The same existing extraction profile is used; this feature does not change the corpus or require an index rebuild.

```json
{"ids":["<item UUID>"],"projection":"summary","maxBytes":65536}
```

The response has `extractionProfile`, caller-scoped `state`, `list`, `notFound`, `remainingIDs` and `oversizedIDs`. Each record identifies `itemID`, `revisionID`, `isDeleted`, `sourceHash`, `sourceUTF8Bytes`, `ftsUTF8Bytes`, and separate `index.fts` / `index.semantic` diagnostics. `sourceHash` is the inline projection’s content identity, not a checksum of raw text bytes; treat it as opaque. The response also describes root exclusions and ignored value types. Non-text/date values and references/bytes are omitted from extraction, and references or attachments are never followed. Ordinary nested text with an operational-sounding key remains eligible; exclusions apply at the root only. Blank metadata leaves and blank assembled-source sections are omitted. The FTS subject/body strings still preserve their original bytes, including whitespace, so their byte counts can be nonzero when no source section is emitted.

`maxBytes` is 8192–524288, default65536. It bounds the independently encoded native method result, including continuation/error-ID arrays, not the surrounding native/MCP framing. Follow `remainingIDs` with the same projection and compare state. A record that cannot fit alone appears only in `oversizedIDs`; use `summary` to inspect it. Text is never silently truncated or replaced by an incomplete record. If a record fits alone but not with its continuation, `responseTooLarge` tells the caller to request that ID alone, narrow the projection or increase the budget. Missing and unreadable items share `notFound`, with no extracted content or item-specific index details.

FTS status is `current`, `stale`, `missing` or `unavailable`. Its scope is ordinary owned values: it compares their actual bounded indexed text against canonical fields; old index text and SQLite error details are not returned. `searchEligible` describes the inline projection and excludes deleted or empty inline source; it does not describe saved v2 page eligibility. It does not promise a match for a particular tokenizer, query, category filter or permission scope.

Semantic status is `disabled`, `notIndexable`, `pending`, `missing`, `stale`, `current` or `unavailable`. It reports the applicable configuration/profile and chunk parameters when those are readable. `current` requires both the content hash and revision binding to agree, with stored records present. Matching text alone is insufficient. A configuration that cannot be read reports unknown `enabled` as null; index faults are not treated as proof that the model is disabled.

`sourceText` is the deterministic inline projection and omits saved v2 pages. Current semantic chunking reads bounded labeled corpus units, so this projection is not its complete assembled input. Chunk sizes/overlap are byte parameters, not token limits; diagnostics do not compute embeddings or return vectors. Normal server background maintenance may continue. Extracted source can be available while either derived index is absent, stale or unavailable. Use actual search results to assess retrieval, rather than treating extraction or index freshness as a relevance guarantee.

## Literal and semantic search

`text` is a literal FTS5 phrase, not raw FTS syntax. It searches subject, body, and owned tagged-text metadata: for example `workingNotes`, `checklists`, `labels`, and arbitrary custom text fields. `tractanda.item-text.v5` emits subject/body first, then sorted root fields and current matching saved attachment text; object keys sort and list order remains. The following exclusions apply **only at the root**:

`itemID`, `revisionID`, `classID`, `schemaVersion`, `createdAt`, `modifiedAt`, `supersedes`, `actor`, `operationID`, `requestIdentity`, `isDeleted`, `permissions`, `accessConfiguration`, `categoryOverrides`, `personalOverrides`, `categoryParents`, `selection`, `viewDefinition`, `learningFeedback`, `learningSettings`, `developmentUUIDMigration`, `templateKey`, `attachments`, `attachmentText`, `attachmentDocument`.

Empty or whitespace-only text values are omitted together with their field labels. Nonblank values retain their original bytes. A nested ordinary field with one of those names remains owned text. Extraction never traverses references, opens original attachment payloads, invokes a converter, or reads remote content. Explicit saved attachment text and document output participate under the matching-descriptor rules below. Named metadata SQL predicates are a separate query mechanism.

Semantic retrieval is optional and uses the same owned-text corpus as FTS5. The single input encoding is `item-text-utf8-v2`; the earlier subject/body-only prototype mode has been removed. The current extraction rules are `tractanda.item-text.v5`. Extraction-rule versions participate in the semantic profile identity, so a rules upgrade rebuilds the disposable vector index without changing the model, canonical records or item history. Before asserting semantic coverage, agents should inspect `TractandaSemantic/status`, especially `inputEncoding`, `itemTextProfile`, coverage and index counts. LSM query behavior is unchanged.

Semantic configuration, rebuild and reset are administrator operations. The embedding endpoint is an operational loopback configuration, not a query-supplied URL. Semantic filtering still applies current permissions and the same category/query constraints.

With native feature `tractanda.semantic-job-timing.v1`, semantic search starts a caller-scoped job with a fixed **120-second lifetime from creation**. Successful search and pending/ready/failed result states include `createdAt` and `expiresAt`; pending states also include `retryAfterMilliseconds` (currently 500), a polling interval rather than a prediction of remaining latency. The `at`/`timeZone` evaluation clock does not affect expiry, and polling never renews it. Jobs live in native-server memory: the same principal may resume polling after a stdio adapter restart, but a native-server restart loses them. Model/profile changes and index reset/rebuild may invalidate jobs earlier. Retain your query's expiry: `notFound` errors omit timing and deliberately do not distinguish expired, unknown or foreign jobs. Start a new search. Without the feature declaration, do not assume newer compiled adapter documentation describes the connected server.

## UUID node policy

UUIDv1 values intentionally encode a time and node provenance value. Production must use a real eligible host node (or explicitly configure the issuer node where hardware identity is unavailable). CI's synthetic node exists solely for disposable test fixtures and must never be copied into production configuration.

## Originals and attachment lifecycle

Native feature `tractanda.attachment-lifecycle.v1` supports originals on ordinary items. The reserved root `attachments` tagged list contains strict descriptors: `attachmentID` (lowercase UUIDv1), `filename` (display metadata), `mediaType`, `byteCount` (exact Int64) and `sha256` (lowercase hex). Item get/query/history return descriptors without original bytes. Generic commits cannot create, alter, remove or rebind this list. Copy reads the authorized source and streams independent originals into new attachment identities before committing its new, initially private item history; replay returns that same copy.

| Method | Arguments and result |
| --- | --- |
| `TractandaAttachment/begin` | `itemID`, `expectedRevisionID`, `operationID`, `filename`, `mediaType`, `byteCount`, `sha256`; returns `uploadID`, `attachment`, `offset`, `chunkBytes`, `expiresAt`, or `committed` for a canonical replay |
| `TractandaAttachment/upload` | `uploadID`, sequential `offset`, base64 `data`; returns acknowledged `offset`; identical written bytes can be retried |
| `TractandaAttachment/finish` | `uploadID`; validates/publishes immutable original, then commits the referring guarded revision; returns compact lifecycle receipt |
| `TractandaAttachment/uploadStatus` | `uploadID`; current-authorized phase, verified/total byte counts and retry delay |
| `TractandaAttachment/integrity` | `itemID`, optional `revisionID`, `attachmentID`; current-authorized original integrity status |
| `TractandaAttachment/abort` | `uploadID`; cancels integrity work and discards unpublished stage only |
| `TractandaAttachment/list` | `itemID`, optional `revisionID`; returns that revision's descriptors |
| `TractandaAttachment/content` | `itemID`, optional `revisionID`, `attachmentID`, `offset`, `limit`; returns bounded base64 `data`, descriptor, `nextOffset`, `isComplete` |
| `TractandaAttachment/detach` | `itemID`, `expectedRevisionID`, `attachmentID`, `operationID`; commits a new descriptor list and returns a compact receipt, retaining all historical originals |

Lifecycle receipts contain `itemID`, `revisionID`, optional `supersedes`, `operationID`, `replayed`, `indexReady` and `warnings`. They omit parent content and retry-intent bytes; fetch the item explicitly if its content is needed. Begin replay nests this compact receipt in `committed`.

Native feature `tractanda.attachment-transfer.v2` removes the original format-size ceiling: byte counts and offsets use checked nonnegative signed 64-bit integers. Transfers remain **256 KiB per chunk and 128 attachments per item**. Base64 expands one full chunk to about 350 KiB within the existing 8 MiB envelope. The default operator quota is eight active transfers per caller, 64 total and **8 GiB of actual staged bytes**, independent of an original's declared total size. Configure actual staging allowance with `--attachment-staged-byte-quota N`; a larger original needs enough quota and genuine available disk capacity to finish. No quota removes the per-write free-space guard.

Idle retention defaults to one hour and is configurable with `--attachment-upload-idle-seconds N`. Successful append, byte-identical chunk retry and identical begin/resume renew retention. Total elapsed transfer duration does not expire an active upload. Private bounded recovery records and synchronized original stages survive server restart; identical begin resumes the same upload ID and acknowledged offset. Restart validates intent and stage metadata. Abort/idle cleanup synchronizes an explicit discarding tombstone before unlinking a stage, and startup completes interrupted cleanup. Physical published location is retained independently of checksum phase; if publication preceded its operational checkpoint, restart rediscovers the descriptor-bound immutable payload before any stage lookup. Committed canonical dependency corruption still fails validation. Explicit abort and subsequent idle-expiry cleanup remove only unpublished stages and their operational records. Every lifecycle/status call rechecks current item authorization before metadata or payload access. Committed begin replay requires current read permission; active upload/status/finish requires current edit permission. Final publication and commit recheck authorization and the expected revision.

Retain the complete begin intent and operation ID. Successful finish releases active transfer capacity; repeating finish with the released transient ID reports `uploadExpired`. After a lost finish reply, repeat begin with identical arguments: a committed operation returns its canonical receipt without re-uploading. An unfinished transfer resumes acknowledged bytes. Interrupted publication or a CAS conflict can leave unreachable immutable bytes; physical reconciliation/purge remains future work. Changed intent under a committed/staged operation ID is rejected. Publication failures never create a revision referring to missing or incomplete bytes.

Daemon finish and cold original-content reads start one shared bounded off-queue SHA-256 task per original/upload. While pending, the server immediately returns `attachmentVerifying` with `retryable: true`, `phase`, `attachmentID`, optional `uploadID`, `verifiedBytes`, `totalBytes` and `retryAfterMilliseconds` (100). Retry the identical finish/content request or inspect `uploadStatus`/`integrity`; no all-original response deadline is imposed. The native and portable clients retry only this condition and check cancellation between short requests. Disconnecting does not cancel accepted hashing. Shutdown cancels and waits hashing between bounded chunks; restart retains the upload as paused, and another finish safely restarts validation. During phase `verifying`, `verifiedBytes` reports bytes examined by the running checksum; the whole-original digest is accepted only after hashing completes. Phase `verified` means byte integrity succeeded, not that a referring item revision committed; finish still performs current ACL/CAS checks. A checksum failure is terminal for that upload and returns `attachmentIntegrity`; abort and begin a corrected intent.

Finish, content and abort require a singleton native envelope in the daemon; a batch receives `attachmentSingletonRequired` for those calls instead of falling through to blocking hashing. Ordinary metadata/query batches remain supported. The legacy synchronous network `serve` command rejects original finish/content with `attachmentRequiresDaemon` and guidance to use `tractanda daemon STORE SOCKET --no-http`; it does not advertise the v2 asynchronous transfer contract. Direct synchronous `ItemStore`/in-process `ItemService` operations are offline blocking library APIs; the asynchronous daemon uses prepared integrity work. Daemon attached-item copies now prepare independent bytes off-queue and return retryable `attachmentCopyPending` until a fresh source ACL/CAS finalization succeeds. Native/portable clients repeat the exact guarded request with cancellation. Batches and the old synchronous network path cannot fall through to blocking copies; use one daemon copy call. Committed replay retains its current-target read check. Rebuild progress is the next bounded integration unit.

Original reads use a bounded 128-entry integrity cache keyed by exact descriptor and immutable file metadata. An off-queue streamed SHA-256 check anchors first validation. Opened metadata is checked before/after each bounded read; changed or evicted signatures require another shared verification task instead of owner-queue hashing. CLI exports verify the complete streamed output hash/size before publishing the destination. This remains application-enforced immutability; it cannot detect an external privileged actor rewriting bytes while deliberately preserving every observed metadata signature.

The MCP adapter exposes two read-only tools when attached to a server declaring `tractanda.attachment-lifecycle.v1`:

| Tool | Native method | Arguments and behavior |
| --- | --- | --- |
| `tractanda_attachments` | `TractandaAttachment/list` | Required `itemID`, optional `revisionID`; returns descriptors for the requested readable revision. |
| `tractanda_attachment_content` | `TractandaAttachment/content` | Required `itemID` and `attachmentID`, optional `revisionID`, byte `offset` (default 0) and byte `limit` (default 4096, range 1–65536). Returns base64 original bytes, descriptor, `offset`, `nextOffset` and `isComplete`. |

The adapter checks fresh `TractandaStore/info.features` before each call. Missing support returns `unsupportedCapability`; an absent or invalid declaration returns `featureUnverified`. It does not infer support from its own build. The native service rechecks current permissions on every chunk, including historical reads. A missing attachment returns `notFound`, while an ACL denial retains the native `forbidden` code; either error returns no descriptor or payload. For stable reconstruction, use the list result's `revisionID` on every continuation call; follow `nextOffset` through `isComplete`, concatenate decoded bytes in order and compare total bytes and SHA-256 to the returned descriptor. Offsets count original bytes, so a chunk may split a multibyte UTF-8 character. MCP adds no path argument or filesystem access. Its 64 KiB content ceiling keeps base64 output comfortably below the 512 KiB native result limit; results are returned in the selected MCP text/structured format without truncation.

CLI examples (use `--profile production` in normal local use; these examples take an explicit socket):

```sh
tractanda attach SOCKET ITEM_ID BASE_REVISION OPERATION_ID FILE application/pdf
tractanda attachments SOCKET ITEM_ID
tractanda export-attachment SOCKET ITEM_ID ATTACHMENT_ID DESTINATION [REVISION_ID]
tractanda detach SOCKET ITEM_ID BASE_REVISION OPERATION_ID ATTACHMENT_ID
tractanda export-item SOCKET ITEM_ID DESTINATION_DIRECTORY
```

Import opens a regular local file without following a leaf symlink, hashes/streams fixed chunks and sends no source path to the server. Export requires a new destination, retains a genuine 1 GiB runtime available-byte reserve, and stages output beside the destination. `export-item` includes `revision.json` plus each referenced `<attachmentID>.original`; display filenames never define output paths. MCP now exposes read-only attachment listing and bounded content retrieval; native client/CLI retain upload and export workflows. UI editing remains future work. Root `attachments` manifests are excluded from text/vector input, including filenames and hashes. Explicit saved UTF8 and document representations are projected separately as described below.

The unshipped attachment runtime uses a **1 GiB filesystem-available reserve** before each payload/export write. Tests use a separate conservative **10 GiB reserve** plus small fixture caps. These working-data guards are separate from provisional installation headroom; large originals require their own additional storage. Historical foundation receipts used the earlier 10 GiB runtime guard and are retained as evidence of that source version.

## Deterministic UTF8 extraction and source citations

CLI `describe SOCKET [TOPIC]` calls `TractandaStore/describe` (default overview; types/properties are also supported). `extracted-text SOCKET ITEM_ID...` calls the existing bounded `TractandaItem/extractedText` source projection and preserves continuation/oversized results. Use these wrappers or the native method names with `call`; MCP tool names are not native method names.

For current UTF8 citations, take item/revision/attachment/representation/hash and exact original byte ranges from the delivered `sources` map's `originalBytes` location. The saved representation's `source.revisionID` is extraction-input provenance, distinct from the current locator after extraction or copy. An older provenance revision may still address the same immutable original in a simple fixture; it must not be substituted for a delivered current locator. Image/PDF citations use document regions as described below.

Native feature `tractanda.attachment-text.v1` adds `TractandaAttachment/extractText` with `itemID`, `expectedRevisionID`, `attachmentID` and `operationID`. It returns the compact attachment lifecycle receipt. CLI: `tractanda extract-attachment SOCKET ITEM_ID BASE_REVISION OPERATION_ID ATTACHMENT_ID`. Exact retries use the original expected revision and operation ID; committed replay checks current read permission before returning its receipt and does not decode/read the original again. New extraction requires current edit permission and the expected head; unsupported media, malformed UTF8, limits or CAS conflicts do not change the item/original.

Only `text/plain` and `text/markdown` originals of at most **512 KiB** are supported. The decoder removes one leading UTF8 BOM and records source byte base 3; otherwise the base is 0. CRLF, Unicode, NUL, nonleading BOM and all other source bytes are preserved; Markdown is saved as source rather than rendered. There is no encoding guessing, truncation, OCR or model conversion. The reserved root `attachmentText` list retains complete saved output, UUIDv1 representation identity, converter `utf8-v1`, schema `tractanda.attachment-text.v1`, tagged extraction date and input item/revision/attachment/hash/byte-count/media provenance. Aggregate encoded representations are capped at **2 MiB/item** within the existing **8 MiB record** ceiling. Generic commits cannot forge or clear this list.

Current text profile `tractanda.item-text.v5` uses one shared FTS/semantic projection for owned prose, saved UTF8 and historical v1 inline page text. New v2 page-tree FTS/semantic projection is an explicit pending integration; it must be completed before the attachment batch is accepted. IDs, hashes, filenames, converter bookkeeping and duplicate structured metadata remain excluded. A representation participates only when its local attachment ID/hash/size/media matches the current descriptor. Detach retains canonical output/history while excluding that text from the current corpus. Copy preserves saved text/provenance and remaps active locators to its byte-identical independent originals with fresh representation IDs; provenance does not cause foreign-history traversal.

`TractandaItem/extractedText` includes bounded `sources` maps with current `itemID`/`revisionID`, `attachmentID`, `representationID`, `sourceSHA256`, and `corpusByteStart`/`corpusByteEnd`. Every entry has one discriminated `location`: `{"kind":"originalBytes","byteStart":N,"byteEnd":N}` maps UTF8 text to exact original bytes; `{"kind":"document",...}` identifies a page/block/raster region for converted image/PDF text and has no original-byte offsets. The list can contain both kinds. It also reports attachment representation coverage. These maps accompany source/FTS/summary diagnostics and obey their response budget. Large source text can be marked oversized; the ordinary compact item summary omits these heavy reserved fields. Current permissions govern all saved output, historical reads, diagnostics and search results.

Semantic passage `byteStart`/`byteEnd` remain offsets into the shared corpus. Its `sources` list contains overlaps with attachment text: current owner item/revision, attachment/representation IDs, source hash, typed `location`, and the corresponding corpus interval. For UTF8 extraction, `location.kind` is `originalBytes` and includes exact byte bounds, including the three-byte base after a stripped leading BOM. For image/PDF conversion it is `document` and identifies a page/block/raster region; it does not contain binary byte offsets. A passage may cite multiple source segments or have an empty list. Labels and ordinary body text have no invented attachment locations. Immutable semantic snapshots carry these segments; delivery still rechecks current content and ACL. Default 384-byte chunks and 64-byte overlap are unchanged.

## Bounded document extraction

This is an experimental macOS opt-in. The 7 October native trial did not establish general OCR readiness: its PNG produced an unsupported picture-only block, one PDF paragraph was omitted and another repeated, and the PDF table cells appeared as ordinary text without an OTSL table. These are recorded recognition/coverage failures, not a promise that admitted images or PDFs will extract accurately. Native Linux conversion is unverified. The 10 October Swift correction independently matches the measured official C input pixels, native BF16 values, variable-grid prompts and crop geometry. Its bounded native rerun committed both originals: portrait text improved to all three required facts in order; PNG emitted three text lines but retained zero of four exact phrase matches because the title was missing and words lost spaces. The landscape still emitted ordinary cell text without OTSL. These fixed-fixture results preserve the existing recognition criteria and do not establish inference/backend equivalence or general OCR readiness.

Only a single `extractDocument` envelope selects a 390-second local socket response wait for the server's 360-second conversion and cleanup bound. Ordinary connect, send and other response waits retain their 15-second defaults. The optional operator startup `--document-preparation-directory` gate selects independently frozen input captures by original SHA; it is off by default and cannot be supplied by a request.

Native feature `tractanda.attachment-document.v1` adds `TractandaAttachment/extractDocument` (`itemID`, `expectedRevisionID`, `attachmentID`, `operationID`) and returns the compact `AttachmentCommitResult`. Exact retries use the original revision and operation ID; replay is checked before conversion. The call accepts no client-supplied converter, model path, or output. The portable client exposes `extractAttachmentDocument(...)`. CLI: `tractanda extract-document SOCKET ITEM_ID BASE_REVISION ATTACHMENT_ID OPERATION_ID`.

`TractandaAttachment/document` reads a saved canonical extraction using `itemID`, `attachmentID`, optional `revisionID`, optional `pageNumber`, and `maxBytes` (4096–4194304, default 1048576). Its `AttachmentDocumentReadResult` includes delivered item/revision/attachment/representation identity, immutable source provenance, converter identity, total page count, optional selected page number, and returned page content. A page selection is a bounded read of a complete saved representation; it is not a partial representation marked complete. The complete structured page must fit the requested response cap and transport envelope or the call fails with `responseTooLarge`; no fields or blocks are silently truncated. CLI: `tractanda attachment-document SOCKET ITEM_ID ATTACHMENT_ID [--revision REVISION_ID] [--page N] [--max-bytes N]`. The client wrapper is `attachmentDocument(itemID:attachmentID:revisionID:nil,pageNumber:nil,maxBytes:1048576)`.

### Durable document jobs and MCP page access

Native feature `tractanda.document-jobs.v1` declares the durable `TractandaDocumentJob` methods `start`, `status`, `cancel`, `resume`, `rebase`, `page`, `discard`, and bounded `list`. Start takes itemID, expectedRevisionID, attachmentID and operationID; exact retries use the same actor-scoped operation ID and payload. Status/list and controls retain native current ACL, actor ownership and administrator rules. A declared feature confirms method routing only: converter readiness, source availability and current permission remain independent. Status/recovery remains callable when the converter is paused or unavailable.

A controlled native watchdog timeout may add optional status `reasonMessage`; existing `reasonCode=documentTimeout` is unchanged. The message (at most 512 UTF-8 bytes) reports observed phase or `unknown`, timeout kind, budget and elapsed time. It clears when the reason changes or the job resumes, contains no raw stderr or document content, and may be absent on older servers.

The MCP adapter exposes `tractanda_document_job_start`, `tractanda_document_job_status`, `tractanda_document_job_cancel`, `tractanda_document_job_resume`, `tractanda_document_job_rebase`, `tractanda_document_job_page`, `tractanda_document_job_discard`, and `tractanda_document_jobs` only through the native feature gate. After publication, use `tractanda_attachment_document_page`, which calls `TractandaAttachment/document` with a required explicit pageNumber and optional pinned revision. It returns canonical identity, source provenance, total page count and that selected page. It cannot request a whole representation.

The native JSON result must fit its 512 KiB limit, and the adapter also bounds the serialized MCP content/structured wrapper with frame headroom. Either check can return `responseTooLarge`; no page fields are silently removed or truncated. Lower maxBytes, request a bounded document/source window where supported, or read original bytes in verified chunks. A stale running adapter has static tools/resources; restart it after upgrade and rediscover tools. Its compiled reference and listing are not evidence that the connected native server declares either feature.

### Bounded exclusive store rebuild

Native feature `tractanda.store-rebuild.v2` declares singleton daemon methods `TractandaStore/rebuild` (`operationID`, 1–200 UTF8 bytes), `TractandaStore/rebuildStatus` (optional `jobID`, latest job by default), and `TractandaStore/rebuildCancel` (required `jobID`). Admission returns immediately with a UUIDv1 job ID; a repeated operation ID joins/replays the current retained job. The bounded journal keeps the latest job only. Every admission/status/cancel resolves current OS administrator membership. Revoked accounts receive no job metadata. HTTP session authorization uses fresh OS identity/admission lookup outside the occupied Store queue during exclusive rebuild. Index publication refreshes administrator authority again.

Ordinary requests return `serviceBusy` while accepted readers and background original/copy producers drain and the Store rebuild runs exclusively. Earlier background publication is fenced by a coordinator generation. Status and cancellation remain available without waiting for the Store queue. Rebuild continues after client disconnect. Daemon shutdown requests cooperative background stop before awaiting Store-backed maintenance, then drains accepted listeners/readers/producers before releasing writer ownership. Explicit cancellation is cooperative at bounded record, original-hash chunk, document node/page and canonical file/directory synchronization boundaries; no thread is forcibly terminated. An uninterruptible filesystem/SQLite call remains `stopping` until it returns.

Status contains state/phase, checked Int64 record/original-byte/document-page/projected-item/durability-entry counts, update time, no-progress timeout, `indexTrusted`, `requiresRecovery`, and an optional stable error code. Progress is synchronized on phase changes, at most one second between progressing work batches, and at terminal transitions. There is no total rebuild deadline. Default no-progress allowance is 120 seconds (`--rebuild-no-progress-seconds`); unchanged heartbeats do not renew it.

Before replacement begins the canonical checkpoint is marked dirty. Cancel/failure after that point leaves the disposable index untrusted and requires completed recovery. Startup restreams canonical items and all saved v2 dependencies; it never reuses a partial SQLite cursor or reruns OCR. V2 closure traversal retains bounded nodes/pages and uses temporary SQLite ownership registries. Interrupted job status becomes `interruptedRecovered`/`startupRecoveryCompleted` only after successful startup recovery; prior terminal failure/cancellation remains recorded while current index trust is updated. Startup recovery still precedes daemon readiness. Direct offline `ItemStore.rebuildIndex()` is synchronous; the legacy `serve` network path rejects rebuild and must be retired in the client integration stage.

CLI commands are `rebuild SOCKET [OPERATION_ID]`, `rebuild-status SOCKET [JOB_ID]`, and `rebuild-cancel SOCKET JOB_ID`. Supply a stable operation ID to recover a lost admission reply. Full CLI journal/progress UX remains the normal-client stage.

Upload status includes optional `staging` usage: `originalBytes`, `checkpointBytes`, `bookkeepingReservedBytes`, and `maximumStagedBytes`. Original bytes remain charged after physical publication until item CAS succeeds and recovery intent removal is synchronized, or the intent is durably disposed. Startup reconstructs retained canonical originals from validated pending intents. Encoded upload checkpoints are explicitly bounded to 16 KiB; each admitted upload reserves that much bookkeeping headroom for atomic status/tombstone replacement. Actual file bytes and reserved headroom are separate counts. Lowering the operator quota does not prevent reopening retained work, committed replay, expiry or bounded cleanup; it does prevent new payload/admission work that does not fit. Checkpoint writes still obey the configured filesystem-available reserve. This is an operator resource budget, not an arbitrary original-size ceiling.
