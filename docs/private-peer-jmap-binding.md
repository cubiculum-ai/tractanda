# Private peer JMAP binding

Source/private implementation; not deployed. This replaces the personal framed application payload, not its TLS profile or canonical formats. The required hello is `tractanda.personal-sync.v3`, frame version 4, with opted capability `https://tractanda.ai/ns/private-peer/1`. Previous v2 hello/wire peers are rejected; deployment must be coordinated later. No compatibility shim or HTTP client is introduced.

The existing authenticated TLS/PSK/PFS/PQ connection, pairing/store/replica binding, hostname alternatives and responder ready reservations remain authoritative. Either endpoint issues requests over the same connection; each has one outstanding request per direction. Each outer Request may batch up to 16 methods through shared sequential execution and result references; the existing driver continues to send singleton requests. Both finite-cut pull drivers keep running. A successful initiated connection therefore suffices even if its responder cannot dial back. This is a private binding of the shared JMAP API engine, not RFC 8620 certificate-based HTTPS or RFC 8887 WebSocket.

Every peer domain request is a shared JMAP Request with at most 16 ordered method calls, an opted private capability and `accountId` equal to the authenticated logical StoreID. Method arguments/results are structured JSON, adapted explicitly to the existing internal gateway:

| Method suffix (`TractandaPeer/…`) | Arguments besides accountId | Structured result |
|---|---|---|
| inventory | offset, limit; optional snapshotID, knownGeneration, afterRowID | snapshotID, generationID, cutRowID, entries, optional nextOffset, complete |
| inventory.close | snapshotID | closed |
| dependencies | descriptor, offset, limit | entries, optional nextOffset, complete |
| read | descriptor, offset, limit | bytes (base64 binary chunk only) |
| membership.ready | preparation object | configurationDigest, nonce, replicaID, administrator |
| sync.ready | none | ready |

Descriptors expose kind, id, byteCount, sha256, itemID/parentRevisionIDs, and structured attachment/document-part metadata where applicable. They are never base64 JSON blobs. For losslessness, the schema's Int64 offset/afterRowID/cutRowID/nextOffset, descriptor and attachment byteCount, and document ordinal use canonical nonnegative decimal strings. Bounded small limit/level fields remain JSON integers. Membership preparation/readiness metadata has no Int64 numeric fields and retains its explicit Codable object schema. Canonical revisions, hashes and stored data remain unchanged. Generic JMAP clients can inspect fields and descriptor IDs directly; no arbitrary JSON tree rewriting is performed.

The shared built-in Core/echo remains valid with Core-only opt-in after current authenticated peer eligibility is checked; this session-scoped method grants no content read privilege. There is no remote prepare/append/finish/apply, user/native-method dispatch, sender-selected UID, path or baseline. Local driver intake continues through the existing Store owner. Current membership/control-only/content eligibility and exact gateway argument validation remain authoritative. Capability opt-in cannot grant trust.

The 256 KiB bound applies only to actual raw chunk bytes, not all JSON metadata. Metadata follows the domain's finite pages and the complete framed response budget. An excessive dependency response is a method responseTooLarge and can be requested more narrowly; the current driver already walks one dependency per step. Snapshot admission uses the actual Store inventory contract: descriptor JSON totals at most 128 KiB across at most 128 entries. The explicit wire descriptor schema differs only by at most six added quote bytes for three Int64 strings per descriptor, while compact encoding removes existing pretty whitespace. Add a comma allowance per entry plus an exact worst-case inventory header (UUID snapshot, at most 200 UTF8 generation bytes with worst JSON escaping, Int64 cut/next-offset strings, Boolean), then the exact method/call-ID tuple overhead. This finite success bound is reserved before snapshot open/close. Unexpected malformed/over-bound snapshot output is serverPartialFail defect containment, not an ordinary post-effect size error.

Request-level JMAP Problems occupy an outer `failure` frame with their typed `urn:ietf:params:jmap:error:*`/status body. Ordinary method errors, including `serverPartialFail`, remain inside a `response` frame's JMAP `methodResponses`. Authentication/connection eligibility failures retain the distinct binding failure object. The caller's adapter validates the single method/call correlation and canonical byte encoding; it preserves method-error codes and typed request Problems instead of replacing them with a generic operation error.

The existing codec caps encoded JSON frames at 2 MiB, plus the four-byte length prefix. Its Data body is base64; the canonical encoder uses `withoutEscapingSlashes`. Before application work, the binding derives the maximum inner byte budget as `3 * floor((frameCap - largestEmptyEnvelope) / 4)`, using the longest kind name and `UInt64.max` correlation to cover every personal frame. Kernel request and complete-response budgets use that limit, including their own envelopes/call IDs/Session metadata. Snapshot tuple bounds include exact correlation strings and structured metadata; binary read results include inner base64 expansion in the shared response accounting. A typed response is therefore admitted against the actual outer-frame budget before effects; no generic8 MiB Kernel default leaks onto the2 MiB peer wire.

Node Session metadata is a digest of the private capability, StoreID, pairing ID, current membership digest and enforced request/response/chunk/depth/call limits captured before invocation effects. It is separate from item content state and does not advertise public Session/resource URLs. No index, ledger, credential or membership authority becomes item content. Finite catalogue cuts, generation-reset/rescan, ancestry, staging/acceptance separation, current ACL/stale-author review and merge/recovery semantics remain in the existing Core gateway/intake.

Limits and cancellation retain the generous finite configured peer budgets. One outstanding request and the frame cap bound admitted application work; they are not a new claim about arbitrary socket slow-reader buffering. Existing NIO connection ownership/write failure behavior and alias reservation cleanup remain in place. Focused source/private qualification and its limits are recorded under `work/jmap-alignment-20261025/peer/binding/`; no live success or full network JMAP conformance is implied.
