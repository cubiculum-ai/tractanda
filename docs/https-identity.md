# Built-in ordinary HTTPS identity backend

`TractandaHTTPSIdentity`, in the existing `Packages/TractandaPeerTLS` package, is the ordinary certificate-authenticated TLS identity backend. It does not start a listener. Server routing, public Session URLs, HTTP authentication and resource handlers must integrate and qualify it separately before ordinary network JMAP is available. It does not change the certificate-free private PSK peer binding.

An administrator configures fixed DNS hostnames and an existing identity. Tractanda does not issue certificates, create a CA, run ACME, change DNS, install a proxy, change Keychain ACLs or export protected private keys. The listener must never infer its public hostnames, identity or security policy from request Host or forwarding headers. Trust roots are not a server identity. A pre-existing authenticated HTTPS proxy is a separate optional exposure policy.

## Listener-facing contract

Create `HTTPSIdentityConfiguration(hostnames:trust:)` and a `HTTPSIdentityLoader`. Configured DNS references are ASCII hostname labels, normalized to lowercase; valid single-label private names such as `localhost` or `host` are allowed. Empty/malformed labels, wildcard reference names, trailing-dot forms, non-ASCII input and numeric IP literals are rejected. Certificate SAN matching remains case-insensitive, with no Common Name fallback. On a management worker, call `loadPEM(certificateChainFile:privateKeyFile:configuration:now:)` for external certificate-manager PEM files. Paths must be absolute with the default bounded reader. Input files are capped at 1 MiB each, the certificate chain at 16 certificates. Encrypted PEM private keys have no interactive passphrase fallback.

For macOS, call `loadKeychain(selection:configuration:intermediateCertificatesDER:now:lookup:)`. Selection is an explicit System identity domain (the configured default domain is also supported) or an exact selected SecIdentity persistent reference. There is no broad search or arbitrary first-identity fallback. A missing System identity fails. Explicitly supplied issuer certificates supplement the selected identity's leaf; the adapter does not enumerate other Keychain certificates, fetch intermediates or silently replace the configured identity. Administrators must provide the issuer chain required by their clients. The default production lookup is not invoked by private tests.

The actual macOS Keychain adapter requires its hosting daemon to have deliberately disabled legacy Security interaction at the **process** level before lookup/signing: call `SecKeychainSetUserInteractionAllowed(false)` once before starting key-backed services and keep it disabled for the server process lifetime. Check the OSStatus and then `HTTPSIdentityLoader.requireNoninteractiveKeychainProcess()`; it checks `SecKeychainGetUserInteractionAllowed` and fails with `unattendedKeyAccessDenied` if interaction remains allowed. The adapter does not toggle that process-global policy. Its selected key reference also carries an `LAContext` with `interactionNotAllowed = true`. Both checks matter: the macOS Security headers warn that the modern query no-UI control does not cover all legacy Keychain behavior. Each real-key signing operation rechecks the process policy. A daemon must keep that policy disabled throughout Keychain-backed operation. No identity ACL or private-key exportability is changed. Identities requiring touch, login or other interactive authorization are unsuitable for unattended service and fail validation/signing.

The SecKey adapter supports supported P-256/P-384/P-521 ECDSA or RSA keys of at least 2048 bits with RSA-PSS. It advertises only supported TLS signature schemes and validates each with an actual sign/verify matching-key proof before building a context. NIOSSL's custom key hook supplies unhashed messages; the adapter uses Security's corresponding **message** algorithms, which hash exactly once. Provider signing runs on a serial Dispatch worker, away from NIO event loops. There is no RSA decrypt callback fallback. This backend currently selects TLS 1.3 and HTTP/1.1 ALPN. [RFC 8620 section 8.1](https://www.rfc-editor.org/rfc/rfc8620.html#section-8.1) permits TLS 1.2 or later and recommends server support for TLS 1.3 or later.

Loading checks DNS SANs (no Common Name fallback), validity, permitted key use, non-CA leaf, matching private key, and ordering/signatures/validity of supplied issuers. Absence of KU/EKU permits use under X.509 rules; explicit incompatible use fails. The context carries the intersection of every supplied certificate's validity interval: `validFrom` is the maximum notBefore and `expiresAt` is the minimum notAfter. `isValid(at:)` means `validFrom <= time && time < expiresAt`. Publishing a replacement and each new-connection accessor/handler check both bounds, including wall-clock rollback before notBefore or a forward jump to expiry. An invalid replacement retains the prior context; the prior context must independently remain valid at the current time to accept new connections. The default `chainOnly` policy does **not** require the server's own chain to terminate in its host's trusted roots; independent clients verify their own anchors and hostname. Optional administrator constraints are `.system` (macOS Security with network fetching disabled; Linux BoringSSL default CA paths) or `.rootsPEMFile`.

Create `HTTPSIdentityContextStore` and use `reload { try loader.load... }` on the management worker. Reloads serialize validation and atomically replace the immutable context only after success. After acceptance, each new NIO child channel obtains `store.makeServerHandler()` and installs it before HTTP handlers and channel activation. Never reuse a handler across channels. Existing handlers retain their context and established sessions survive renewal. The listener must close a newly accepted channel when identity acquisition throws; it must never substitute cleartext.

The external certificate manager owns renewal and atomic file installation. After an external renewal signal or a listener-owned bounded timer, retry `reload`. Tractanda does not supply a certificate manager, watcher, automatic proxy or ACME scheduler. An incomplete, corrupted, mismatched, expired or otherwise invalid renewal throws a meaningful error and leaves the old context in place. A still-valid old context can accept new connections. Once it expires, new connections fail closed. Identity failure does not require stopping local IPC or the separate PSK listener. The listener must report reload/expiry failures through its own status surface. It must not restart unrelated bindings to recover an ordinary identity.

Private qualification uses ephemeral fixture CAs/leaves and independent NIOSSL clients with full hostname/anchor verification. It does not establish that an identity is configured on Raven, Stash or any other real host, and does not authorize deployment, provisioning, real Keychain access or live listeners.
