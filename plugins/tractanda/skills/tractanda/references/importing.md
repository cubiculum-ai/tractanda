# Import existing records

Use this workflow for an authorized import into an established store. Resolve material mapping questions before bulk writes; an already-approved mapping does not need another permission round for each sample or batch.

1. Identify the source namespace and stable record identifier. Before creating, query for an existing source identifier within the caller's readable scope. Scoped `referenceLabels` can help: literal search finds candidates, then inspect the exact label and scope. Search hits alone do not prove identity, and absence does not prove that another user has no private copy. Operation IDs do not deduplicate a different import or actor.
2. Validate the field mapping and a representative sample, including its visible category/view membership. Use `tractanda_explain` and compare project ∩ status counts with the intended source records. Preserve source timestamps as tagged `originalCreatedAt` / `originalModifiedAt` dates when evidenced; leave unknown times unset. Mark agreed reconstructions and their provenance rather than silently treating inferred times as exact facts.
3. Assign stable operation IDs, for example `<source>-<mapping-version>-<record-id>`, hashing long identities if needed. IDs are nonempty text of at most **200 UTF-8 bytes**, with no NUL characters; they need not be UUIDs or a particular ASCII alphabet. Receipts belong to the authenticated actor within one store.
4. Persist each exact payload and operation ID before sending it. Deterministic IDs alone do not reconstruct the original intent: timestamps, generated references, default fields or mapping changes can change the arguments. If the journal is lost, reconstruct only when every original argument is known; otherwise reconcile source identifiers/current records before deciding what remains to import.
5. Send each complete edit with required `unset: []` when no fields are removed. After uncertainty, retry the identical payload and ID. A replay returns `replayed: true` and the original committed revision, even if a newer head now exists. Current read permissions still apply; response `state` and `indexReady` describe the current store/index.
6. A definite pre-commit validation rejection does not consume an unused operation ID. Corrected arguments may reuse that unused ID; a new ID is not required. This only establishes what happened in the rejected call, not whether an earlier uncertain attempt committed. Reconcile earlier uncertainty before changing the payload or assigning a new ID. An ID that already committed a different intent returns `operationMismatch`.
7. Expect the readable-store `state` token to move during a long import. Restart an inconsistent paginated read if necessary, without repeating completed writes. Reuse confirmed item IDs and guard later edits with the item's own current `expectedRevisionID`. A deliberately changed mapping is a new intent; reconcile previously imported records before choosing create versus revise.

Keep the import journal, source-to-item mapping and verification results. Store useful provenance in ordinary item fields; do not make the database depend on the journal to recover its content.
