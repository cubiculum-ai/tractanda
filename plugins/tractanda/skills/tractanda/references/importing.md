# Import existing records

## Portable memory migration

For a selected directory of memory notes, read [memory migration](https://github.com/cubiculum-ai/tractanda/blob/main/docs/memory-migration.md) before using the CLI workflow, and confirm that the installed client exposes the commands. The overview gives exact arguments and adapter limits. Use the explicit source directory and a stable namespace. The adapters do not scan native Codex or Claude home directories or redirect later writes from those harnesses.

`preview` creates a bounded local plan without contacting the server. `inspect` checks its identities in the connected store, including tombstones, and reports the proposed outcomes without applying them. Apply only after reviewing that report. `apply` and `resume` use the current connected account's ordinary permissions. An imported author, verifier or agent label is data, not a Tractanda user or ACL.

Keep the original directory, saved plan and private journal until the report is complete and you have verified representative Items and original bytes. Apply attaches and reads back the original bytes before marking an Item complete. Resume the exact journal against the same store, endpoint and authenticated account after uncertainty; do not regenerate it as a retry. If the journal is lost, the Item's canonical source mapping can identify completed imports, but it cannot reconstruct an exact pending operation. Reconcile incomplete Items explicitly. Missing source records are reported; source removal never deletes imported Items. A matching tombstone is reported and never automatically restored.

Reports distinguish created, updated, unchanged, local divergence, conflict, duplicate, missing, incomplete, tombstone and failed records. Stop on incomplete, duplicate or conflict outcomes and reconcile them before another write. A local success report does not establish that another peer has received the import. The exporter is a readable portability aid, not a guarantee of complete Tractanda-to-OKF round-trip semantics; inspect the exported fields and diagnostics before relying on it. Neither import nor export changes native memory settings or disables their writers.

OKF v0.2 specifics and unsupported Markdown/YAML/computation semantics are documented in the linked migration overview. Computation declarations remain inert; do not execute them or treat imported trust claims as authenticated evidence.

Use this workflow for an authorized import into an established store. Resolve material mapping questions before bulk writes; an already-approved mapping does not need another permission round for each sample or batch.

1. Identify the source namespace and stable record identifier. Before creating, query for an existing source identifier within the caller's readable scope. Scoped `referenceLabels` can help: literal search finds candidates, then inspect the exact label and scope. Search hits alone do not prove identity, and absence does not prove that another user has no private copy. Operation IDs do not deduplicate a different import or actor.
2. Validate the field mapping and a representative sample, including its visible category/view membership. Use `tractanda_explain` and compare project ∩ status counts with the intended source records. Preserve source timestamps as tagged `originalCreatedAt` / `originalModifiedAt` dates when evidenced; leave unknown times unset. Mark agreed reconstructions and their provenance rather than silently treating inferred times as exact facts.
3. Assign stable operation IDs, for example `<source>-<mapping-version>-<record-id>`, hashing long identities if needed. IDs are nonempty text of at most **200 UTF-8 bytes**, with no NUL characters; they need not be UUIDs or a particular ASCII alphabet. Receipts belong to the authenticated actor within one store.
4. Persist each exact payload and operation ID before sending it. Deterministic IDs alone do not reconstruct the original intent: timestamps, generated references, default fields or mapping changes can change the arguments. If the journal is lost, reconstruct only when every original argument is known; otherwise reconcile source identifiers/current records before deciding what remains to import.
5. Send each complete edit with required `unset: []` when no fields are removed. After uncertainty, retry the identical payload and ID. A replay returns `replayed: true` and the original committed revision, even if a newer head now exists. Current read permissions still apply; response `state` and `indexReady` describe the current store/index. If message-v1 recovery discarded that operation's optional receipt, `retryReceiptUnavailable` is terminal for the old retry: inspect the item/history and do not resend the old intent.
6. A definite pre-commit validation rejection does not consume an unused operation ID. Corrected arguments may reuse that unused ID; a new ID is not required. This only establishes what happened in the rejected call, not whether an earlier uncertain attempt committed. Reconcile earlier uncertainty before changing the payload or assigning a new ID. An ID that already committed a different intent returns `operationMismatch`. After a receipt-less old retry is reconciled, any new edit uses a fresh operation ID and the current expected revision.
7. Expect the readable-store `state` token to move during a long import. Restart an inconsistent paginated read if necessary, without repeating completed writes. Reuse confirmed item IDs and guard later edits with the item's own current `expectedRevisionID`. A deliberately changed mapping is a new intent; reconcile previously imported records before choosing create versus revise.

Keep the import journal, source-to-item mapping and verification results. Store useful provenance in ordinary item fields; do not make the database depend on the journal to recover its content.
