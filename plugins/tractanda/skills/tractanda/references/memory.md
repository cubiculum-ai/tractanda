# Reusable memory and catch-up

Use this guidance when an agent needs to preserve or revisit useful context in a connected Tractanda store. Discover the instance's categories and saved views first. Use ordinary `Item`s, categories, references and views; read the served item/query references for exact fields, query grammar, and current capabilities.

## Capture useful context

Record decisions, preferences, evidence, open questions and handoffs with their source, date and confidence where useful. Keep provenance clear: distinguish a user's decision from an observation, inference or imported claim. Prefer a concise durable record over a transcript dump. Avoid duplicates, low-value activity logs, and repeating facts already maintained in a canonical item. Do not create duplicate status/priority fields when the instance already represents those concepts with categories. For tracked project tasks, follow the project's established human-readable reference-label convention and preserve existing aliases. Ordinary knowledge notes do not need task numbers.

Optional reusable view names may include **Knowledge**, **Decisions**, **Preferences**, **Evidence**, **Questions**, **Handoffs**, **Changed today** and **Recent changes**. Treat these as suggestions, not a required taxonomy; adapt, save or delete views to fit the instance and user's workflow. Ad hoc queries are fine. Personal **Seen**/**Unread** category overrides are manually maintained convenience labels: do not promise that a new revision automatically marks an item unread or that reading a view acknowledges its entries.

Inbox or recipient categories are labels for discovery. The underlying item permissions govern who can read or change content. Agents act through the connected OS user account or authenticated session and its ordinary ACLs, like other users; an agent name does not create an identity, separate authorization layer or provisioning workflow. Ordinary shared folders, chats and email remain ordinary workflows, not Tractanda-specific orchestration.

## Since-last-visit catch-up

Keep a small checkpoint in the agent's existing durable working state, scoped to the relevant store/account and query scope. It is not global server state. Query items created or modified at or after the last successful read cutoff, using only timestamp predicates supported by the connected server's served query grammar. Start with a user-relevant bounded window or project on the first run; broaden with an explicit date, text or semantic query when needed.

Use the query's returned `evaluatedAt`, or the start time of the successful query, as the next cutoff, not the time the query finishes. Hold the same `at` and `timeZone` across pages when the API exposes them. Process the intended scope before advancing the checkpoint. An inclusive boundary may return an item again; compare item and revision when useful. If the read is incomplete or unstable, keep the old checkpoint and report the limitation rather than advancing it.

This timestamp view is a convenience heuristic. Late offline arrivals can have old timestamps and may be missed; deletions are not necessarily represented. Do not treat it as a changefeed, complete audit history or guarantee of catch-up, and do not add an elaborate replay protocol. A view read does not mark every result acknowledged; avoid a global shared `lastAccess` field.

## Incremental Item-change catch-up

When the connected native server declares `tractanda.item-changes.v1`, incremental Item changes can complement timestamp views for current personal/workgroup catch-up. Read `tractanda://reference/query` for exact call shapes and limits. Start from an Item `state` returned by `TractandaItem/get` or a same-caller/account Item state; never use `queryState`. Keep that opaque state in the agent's durable working state, scoped to the same store/account and caller.

For each response, process the `created`, `updated` and `destroyed` IDs under current permissions. If `hasMoreChanges` is true, continue from that response's `newState`. Save a completed checkpoint only after the intended deltas have been processed. Do not advance it to a newer state from a partial get, which could skip changes not yet processed. If the read is incomplete or unstable, retain the prior checkpoint. On `cannotCalculateChanges`, refresh with query/get and establish a new state; do not retry unrelated writes to recover a read token.

The service retains bounded derived metadata, not a durable audit ledger or exactly-once delivery guarantee. Normal personal/workgroup restart preserves valid Item-change states through verified index reuse; restart alone does not require a fresh baseline. An actual recovery rebuild invalidates those states. Age/capacity pruning, a fresh or incomplete index epoch, a mode/profile change or principal remapping can also invalidate states or plans. Current permissions are checked on every page; if a pending changed Item is no longer readable, refresh rather than silently skipping it. Change states are local to their caller/account context and do not transfer between peers. Readable soft-deleted Items remain visible as updates. Keep timestamp views and explicit queries as useful everyday workflows and fallback when incremental states expire or are unavailable.

## Portable memory workflow

The current source branch contains an unreleased, explicit directory-import workflow. It accepts a selected directory using the `directory`, `okf`, `codex` or `claude` adapter, writes an inspectable local plan, and supports journaled apply/resume/report plus a namespace-scoped readable export. Use the [memory migration guide](https://github.com/cubiculum-ai/tractanda/blob/main/docs/memory-migration.md) for exact CLI arguments and format limitations. Confirm the current client exposes these commands before relying on them.

This workflow does not scan Codex or Claude home directories, import a user's private corpus without selection, or redirect native memory writers. Keep source files and existing memory settings until the imported Items and original bytes have been verified. Resume uncertain writes from the same private journal and destination account; a fresh preview is not an exact retry. Review `incomplete`, `duplicate`, `conflict` and `tombstone` outcomes explicitly. Default portable recall includes selected OKF status, freshness, links and provenance claims without bulk raw import metadata. Recall omits recognized incomplete source imports, counts them in `skippedIncompleteImports` and reports truncation; an incomplete imported profile or checkpoint fails recall. Imported author and verification fields are claims, not Tractanda identity or permissions. OKF tags are retained as data/category proposals; they do not automatically create categories or assign Items. Computation declarations remain inert and are not executed.

## Portable collaborator and task context

The unreleased memory workflow uses one ordinary collaborator profile Item across projects and a distinct ordinary checkpoint Item for each task or handoff. A local binding selects the StoreID, profile/checkpoint IDs and optionally one saved view or category path plus capture categories. It holds IDs, not credentials or copied memories. `memory recall` returns one bounded page and reports truncation; it is not a full catch-up feed. Recall's item/query state is local to its caller/peer, not portable. `memory remember` and `memory checkpoint` are explicit writes; they do not record every turn. Writes use private exact-intent journals and ordinary permissions.

Read the [portable memory guide](https://github.com/cubiculum-ai/tractanda/blob/main/docs/portable-memory.md) for command forms, a binding example and bootstrap text templates. The templates are inert examples; they do not edit Codex/Claude settings or redirect native writers. Keep native memories and settings until a selected migration pilot is verified.
